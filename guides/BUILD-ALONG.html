Build the real Download Organizer — file by file#

This is the "type the actual app yourself" guide. At the end you will have the exact same seven files as the finished project, and you will understand what every single block of them does.

It is written for someone who has never written Python before. Every new word is explained. Nothing is skipped. Nothing says "just trust me".

How to use this guide#

The app is seven files. We build them in the right order — each one only uses things the ones before it already explained. For every file you get:

  • What it is and why it exists at all.
  • The code, in chunks. Type each chunk into your editor as you read it. Do not copy-paste; typing is how your hands learn the shape of the language.
  • Why it looks like that — the reasoning behind the choices.
  • A checkpoint — a command to run and the output you should see. If it matches, move on. If not, we fix it before continuing. This is the single most important habit in this whole guide: never build on top of something you have not seen working.

Two guides, two jobs. TUTORIAL.md teaches the ideas by building throwaway mini-versions. This file builds the real app. If a concept here feels too fast, read the matching part of TUTORIAL.md first.

The seven files, and why they are separate#

text
config.py          settings, and where files are stored
patterns.py        works out what a file IS (the detective)
history.py         remembers moves so undo is possible
organizer.py       the engine: decide where each file goes, then move it
make_demo_files.py builds a fake Downloads folder for safe testing
gui.py             the desktop window you click
run.py             the 7-line entry point for the .exe

Splitting the app up is not decoration. Each file has one job, so when something breaks you know where to look, and when you want a web version later you add a new "front door" without touching the engine.

1.4 One thing to know before you start: indentation#

Python does not use { } to group lines. It uses indentation — spaces at the start of a line.

python
if True:
    print("this is inside the if")     # 4 spaces: part of the if
print("this is outside")               # no spaces: not part of the if

Use exactly four spaces. Never a Tab. Mixing them causes errors that are painful to find. VS Code inserts 4 spaces when you press Tab inside a .py file, so it is handled for you — but understand why it matters.

Part 2 — config.py: settings and storage#

This file holds every default setting, plus the two functions that read and write them. Nothing else in the app needs to know where settings are stored — they all ask this file.

Create a new file called config.py.

2.1 Chunk 1 — the docstring and imports#

Type this first:

python
"""Settings, plus where the app keeps its files.

Two things live here:

1. `data_dir()` - the folder the app stores config.json / history.json in.
   During development that's this folder. Once the app is turned into a
   Windows .exe, `__file__` points inside a temporary unpack folder, so we
   switch to %APPDATA%\\DownloadOrganizer instead. That's how real Windows
   apps behave.

2. `load()` / `save()` - read and write config.json, falling back to defaults
   if the file is missing or damaged.
"""

import copy
import json
import os
import sys
from pathlib import Path

Why each line

  • The text in """triple quotes""" at the very top is a docstring — a description of the file. Python stores it as the module's documentation. It is for humans, not the computer.
  • import copy — Python's toolbox for copying data properly. We need it so that when we hand out the defaults, a caller cannot accidentally change the master copy.
  • import json — read and write the JSON format (the text format our settings file uses).
  • import os — lets us look up environment variables, like %APPDATA%.
  • import sys — gives us sys.frozen, which tells us whether we are running as a packaged .exe. We will see exactly how in a moment.
  • from pathlib import Path — loads the Path tool from the pathlib toolbox. Path is how we handle file paths so they work on any computer.

import x versus from x import y. import json loads the whole toolbox, so you write json.dumps(...). from pathlib import Path loads just one tool, so you write Path(...) with no prefix. Same idea, different style.

What is this? A dictionary — a collection of labelled boxes. "source" is the label (the key), None is what is inside (the value). You look a value up by its key: DEFAULTS["min_age_seconds"] gives you 5.

Why the values are what they are

  • None is Python's word for "nothing". "source": None means "no folder chosen yet — fall back to the real Downloads folder". Code later checks if cfg.get("source") which is only true when a real value is set.
  • "min_age_seconds": 5 — a file changed in the last 5 seconds is probably still being written by your browser. We leave it alone.
  • "smart_detection": True — do the "look inside the archive" step. It is slower but smarter, so it is on by default.
  • "min_pattern_files": 3 — one file having a trait is a coincidence; three is a pattern. That is the number that makes the pattern engine trustworthy.
  • "rules": [] — an empty list (note the square brackets). Accepted patterns get appended here later.

True and False are Python's two boolean (yes/no) values. Capital first letter, always.

2.4 Chunk 4 — where files are stored#

Below the DEFAULTS dictionary (make sure you are back at the left margin), add:

python
def data_dir() -> Path:
    """Where config.json and history.json live."""
    if getattr(sys, "frozen", False):        # running as a built .exe
        base = Path(os.environ.get("APPDATA", Path.home())) / "DownloadOrganizer"
    else:                                     # running from source
        base = Path(__file__).parent
    base.mkdir(parents=True, exist_ok=True)
    return base

Line by line

  • def data_dir() -> Path: — defines a function named data_dir. The () means it takes no inputs. The -> Path is a type hint: it tells humans (and editors) that this function hands back a Path object. Python does not enforce it, but it documents intent.
  • getattr(sys, "frozen", False) — asks the sys object for an attribute called frozen. If it is not there, return False. When PyInstaller builds an .exe, it sets sys.frozen = True. So this line is really asking: "am I running as a packaged app?"
  • Path(__file__).parent — __file__ is the path of this script. .parent is the folder containing it. So when running from source, we store files next to the code.
  • Path(os.environ.get("APPDATA", Path.home())) / "DownloadOrganizer" — read the APPDATA environment variable (a standard Windows folder for app data). If it does not exist, fall back to your home folder. Then / "DownloadOrganizer" appends a subfolder. The / operator on Path joins path parts — on Windows it produces a backslash, on Linux a forward slash, and you never worry about which.
  • base.mkdir(parents=True, exist_ok=True) — make the folder. parents=True creates any missing parent folders too; exist_ok=True means "do not complain if it already exists".
  • return base — hand the path back to whoever called us.

Why the %APPDATA% branch exists at all: when the app is packed into a single .exe, the code inside is unpacked to a temporary folder that gets deleted. Saving settings there would lose them on every run. Real Windows apps store data in %APPDATA%, so we do the same.

2.5 Chunk 5 — reading and writing settings#

Add these three functions at the bottom of the file:

python
def config_path() -> Path:
    return data_dir() / "config.json"


def load() -> dict:
    """Read config.json, merged over the defaults."""
    cfg = copy.deepcopy(DEFAULTS)
    path = config_path()
    if path.exists():
        try:
            saved = json.loads(path.read_text(encoding="utf-8"))
            if isinstance(saved, dict):
                for key, value in saved.items():
                    if key == "categories" and isinstance(value, dict):
                        # Merge so a new default category still shows up.
                        cfg["categories"].update(value)
                    else:
                        cfg[key] = value
        except (OSError, json.JSONDecodeError):
            pass  # damaged file -> defaults are safer than crashing
    return cfg


def save(cfg: dict) -> dict:
    config_path().write_text(json.dumps(cfg, indent=2), encoding="utf-8")
    return cfg

config_path() — trivial, but it means the filename is written down in exactly one place. If we ever rename it, we change one line.

load() — the important one. Walk through it:

  1. copy.deepcopy(DEFAULTS) — a deep copy of the defaults. Normally cfg = DEFAULTS would just give a second name to the same dictionary, so editing cfg would corrupt the defaults. deepcopy makes a fully separate copy, nested dictionaries included. This is a classic Python trap.
  2. path.exists() — only try to read if the file is actually there. First run has no file, so we simply keep the defaults.
  3. json.loads(...) — turns the file's text into Python data. read_text() needs encoding="utf-8" so non-English characters survive.
  4. The inner loop copies saved values over the defaults:
    • For categories, it uses .update() to merge rather than replace. Why? If a future version of the app adds a new default category, a user's saved file (which lacks it) should still get it. Merging keeps both.
    • For everything else, the saved value wins.
  5. except (OSError, json.JSONDecodeError): pass — if the file is unreadable or corrupted, do nothing and carry on with the defaults. Never let a damaged settings file stop the app from starting.

save() — json.dumps(cfg, indent=2) turns the dictionary back into text, with 2-space indentation so it is human-readable. write_text writes it.

Part 3 — patterns.py: working out what a file really is#

This is the detective. It does not hard-code Minecraft or anything else. Instead it measures small facts about each file, called signals, and the rest of the app decides what to do with them:

text
type:image              the bytes say it is a picture
ext:psd                 the name ends in .psd
inner:pack.mcmeta       the zip contains a file called pack.mcmeta
name:screenshot         the name contains the word "screenshot"
prefix:IMG_             the name starts with IMG_
version:1.20.1          a version number appears in the name

One signal alone is meaningless. Several files sharing an unusual signal is a pattern — and that is what the app suggests folders from.

Create patterns.py.

3.1 Chunk 1 — docstring and imports#

python
"""The pattern engine.

This is the bit that does NOT hard-code anything about Minecraft. Instead every
file gives off a bunch of "signals" - small facts we can measure about it:

  type:image            it really is a picture (from its bytes)
  ext:psd               the name ends in .psd
  inner:pack.mcmeta     the zip contains a file called pack.mcmeta
  inner:AndroidManifest.xml   the zip contains an Android manifest
  name:screenshot       the name contains the word "screenshot"
  prefix:IMG_           the name starts with IMG_
  version:1.20.1        a version number we found in the name

One signal on its own means nothing. But when a bunch of downloaded files all
share the same unusual signal, that is a pattern - and a pattern is a hint that
those files belong together in their own folder.

`suggest()` counts the signals and proposes folders. The user decides whether to
accept a suggestion; accepted ones become "rules" in config.json and from then
on the organizer files matching downloads there automatically.

Adding a new pattern is data, not code: add a line to FRIENDLY_FOLDERS and it
gets a nice name. Anything not listed gets a name worked out automatically.
"""

import re
import zipfile
from pathlib import Path
  • import re — regular expressions, a mini-language for finding patterns in text. We use it to spot version numbers in file names.
  • import zipfile — read inside .zip archives. This is the superpower: a mod, a resource pack and a random zip are all the same format, and only the contents tell them apart.
  • from pathlib import Path — file paths again.

    (b"7z\xbc\xaf\x27\x1c", "archive"),

What this is: a list of (signature, type) pairs. Each signature is the literal start of a file of that type. Note the b before the quotes: that means bytes, not text.

  • b"\x89PNG\r\n\x1a\n" — the 8 bytes every PNG starts with. \x89 is a byte written in hexadecimal, because it is not a typable character. \r\n is the carriage-return + newline pair, part of the PNG signature.
  • (b"BM", "image") — a two-character signature. It is short, so in theory it could match a text file starting with the letters "BM"; real-world files are rarely that unlucky, and this is a sorter, not a forensic tool.
  • We use a list of tuples (a tuple is like a list but fixed) instead of a dictionary because we check them in order and different signatures map to the same type.

Why bytes and not the file name? Because names lie. We will prove that in a minute.

3.5 Chunk 5 — looking inside an archive#

This is the heart of the "look inside the file" idea.

def _inner_signals(names):

        return any(pred(n) for n in names)

    if "fabric.mod.json" in names:
        out.add("inner:fabric-mod")

    if "package.json" in names:

    if "info.json" in names:

    if has(lambda n: n.endswith(".class")):

    if "modrinth.index.json" in names:
        out.add("inner:modpack")

        out.add("inner:modpack")

The signature: it takes names — the set of file names inside an archive, all lower-cased — and returns a set of signals.

The leading _ in _inner_signals is a convention meaning "internal helper, not for outside use". Python does not enforce it; it is a hint to readers.

Three ideas to understand:

  1. set(), .add(), in — a set is an unordered bag of unique items. We use it because we only care whether something is present, never how many times. "info.json" in names is a membership test.
  2. The inner has(pred) helper — pred is short for "predicate", a function that returns True or False. has returns True if any name inside the archive satisfies it. This saves writing any(... for n in names) twenty times.
  3. lambda n: n.endswith("mods.toml") — a lambda is a tiny throwaway function with no name. It means "given an n, tell me if it ends with mods.toml". You need this because has wants a function to test with, and writing a full def for each of twenty checks would be absurd.

Why these particular names? They are real markers, not guesses:

  • fabric.mod.json only exists in a Fabric mod.
  • mods.toml ends a Forge mod's metadata.
  • pack.mcmeta is in every Minecraft pack (resource or data).
  • AndroidManifest.xml / classes.dex are inside every Android app.
  • word/, xl/, ppt/ are the internal folders of Word, Excel and PowerPoint files (they are zip files underneath!).
  • mimetype + OEBPS/ is how an EPUB book is laid out.
  • info.json is a Factorio mod; about/about.xml is RimWorld.
  • modrinth.index.json or manifest.json + overrides/ marks a modpack.
  • meta-inf/manifest.mf plus .class files means a Java package.

This is the "recognise patterns" part you asked for. Not one line says "put Minecraft files in a Minecraft folder". It says "if a zip contains pack.mcmeta, emit inner:mcmmeta". A different table decides what folder inner:mcmmeta means, and the user can override that. Adding a new game is one line here.

            return name

_read_head: open(path, "rb") opens the file for reading in binary mode (r = read, b = binary). with ... as f: closes the file automatically when the block ends. size: int = 32 is a default argument — call _read_head(p) and you get 32 bytes; call _read_head(p, 8) for 8. If anything goes wrong (a locked file, a permission problem) we return empty bytes b"" rather than crashing. A sorter should never fall over because one file was busy.

magic_type: loops through the table and returns the first type whose signature matches the start of the bytes.

Then three checks that the table cannot do:

  • head[4:8] == b"ftyp" — the MP4 family puts its marker not at the start but at bytes 4–7. head[4:8] is a slice: characters 5 to 8, because Python counts from 0. So this asks "are bytes 5–8 the letters ftyp?".
  • MKV and WebM start with a four-byte marker we cannot write as neat text, so we compare the escaped bytes instead.
  • RIFF is a container: the same four letters begin WAV audio, AVI video and WEBP images. We peek further in (head[8:12]) to tell them apart.

return None means "I have no idea", letting the caller try something else.

def _looks_like_text(path: Path) -> bool:

def signals(info: dict) -> set:
    """Flatten an info dict into the set of signal strings."""
    out = set()
    if info.get("type"):
        out.add(f"type:{info['type']}")
    if info.get("ext"):

    for group in ("inner", "names", "prefixes", "versions"):

    return out

3.15 Chunk 14 — spotting patterns across many files#

def suggest(files, cfg):
    """Look for patterns across a batch of files.

    `files` is a list of (path, info) pairs. Returns a list of suggestion
    dicts, most common first:

        {"signal": "inner:fabric-mod", "count": 8,
         "folder": "Minecraft Mods", "examples": ["sodium.jar", ...]}
    """
    min_files = int(cfg.get("min_pattern_files", 3))
    ext_lookup = cfg.get("_ext_lookup", {})
    taken = {rule["match"] for rule in cfg.get("rules", [])}

    counts, examples = {}, {}
    for path, info in files:
        for signal in signals(info):
            kind = signal.split(":", 1)[0]

            # type/ext are handled by the normal rules. Versions belong as a
            # subfolder, not a top-level folder of their own.
            if kind in ("type", "version"):
                continue
            # An extension we already route somewhere needs no suggestion.
            if kind == "ext" and signal.split(":", 1)[1] in ext_lookup:
                continue
            # Signals that already sort themselves need no suggestion.
            if signal in AUTO_SIGNALS:
                continue
            # A rule already covers this signal.
            if signal in taken:
                continue

            counts[signal] = counts.get(signal, 0) + 1
            examples.setdefault(signal, [])
            if len(examples[signal]) < 4:
                examples[signal].append(path.name)

Counting is the entire pattern engine, and it is simpler than it looks:

  • min_files — how many files must share a signal before it is a pattern.
  • taken — a set of signals the user has already accepted as rules, so we do not keep suggesting them.
  • counts — a dictionary counting how many files carry each signal.
  • examples — up to four file names per signal, so the user can see what we mean.

Every continue is a filter. We skip signals that are useless for suggestions:

  • type: and version: — type is too generic, version belongs in a subfolder.
  • ext: that is already routed by the categories table — no need to suggest what already works.
  • signals in AUTO_SIGNALS — they sort themselves already.
  • signals already accepted as rules.

counts.get(signal, 0) + 1 means "whatever the count is so far (or 0), add one" — the standard way to count things in Python.

def _prune_empty_parents(folder: Path, stop_at: set):
    """Remove folders we emptied, working upwards, never past the stop points."""
    while folder not in stop_at:
        try:
            if not folder.is_dir() or any(folder.iterdir()):
                break
            folder.rmdir()
        except OSError:
            break
        folder = folder.parent

After undo, Images/ is probably empty and pointless. This removes it — then keeps climbing to remove an empty Minecraft/, and so on.

  • while folder not in stop_at: — keep climbing until we reach a folder files actually came from. This is the guard that stops us ever deleting your Downloads folder.
  • any(folder.iterdir()) is True if the folder has even one thing left in it, so we break rather than delete something with files in it.
  • folder.rmdir() removes an empty folder. It refuses to remove one with contents — a second, built-in safety net.
  • folder = folder.parent climbs one level up and loops.

Two independent safety nets. Our stop_at set, and rmdir refusing non-empty folders. Either one alone would be enough; both together mean a bug in one cannot orphan your files.

5.3 Chunk 3 — building the extension lookup#

python
def build_extension_lookup(categories: dict) -> dict:
    """{"Images": ["jpg", ...]} -> {"jpg": "Images", ...}."""
    lookup = {}
    for folder, extensions in categories.items():
        for ext in extensions:
            lookup[str(ext).lower().lstrip(".")] = folder
    return lookup

Our settings store the table one way (folder -> list of extensions) because that is how a human edits it. But the engine constantly needs the opposite question answered — "given jpg, which folder?" — so we flip it into extension -> folder at the start of a run.

  • .items() gives you both the key and value in one loop.
  • str(ext).lower().lstrip(".") normalises each extension: string, lower-case, no leading dot. That way JPG, .jpg and jpg all become jpg.

Doing this once, up front, is a real performance idea. Without it, every file would have to search every category's list. With it, every lookup is a single dictionary hit.

5.4 Chunk 4 — should we touch this file?#

python
def looks_like_download(entry: Path, min_age: float):
    """Return (ok, reason). ok=False means leave the file alone."""
    if entry.name.lower() in JUNK_NAMES:
        return False, "system file"
    if entry.suffix.lower() in PARTIAL_SUFFIXES:
        return False, "still downloading"
    try:
        age = time.time() - entry.stat().st_mtime
    except OSError:
        return True, ""
    if age < min_age:
        return False, f"changed {age:.0f}s ago"
    return True, ""

This is the safety gate, and it returns two values: whether to proceed, and why not. Returning a reason is what lets the app print a helpful "skipped bigfile.zip.part: still downloading" instead of silently doing nothing.

  • entry.stat().st_mtime — the file's last-modified time, as a number of seconds. time.time() is now. Subtracting gives the age in seconds.
  • if age < min_age: — too fresh; the browser is probably still writing it.
  • f"changed {age:.0f}s ago" — :.0f formats the number with zero decimal places, so 3.9142 prints as 4.
  • If stat() fails (a file that vanished between listing and checking) we return True, "" — allow it — because the read step will handle a missing file gracefully anyway.

5.5 Chunk 5 — never overwrite#

python
def unique_destination(dest_dir: Path, name: str) -> Path:
    """Never overwrite - bump to 'name (1).ext' if needed."""
    dest = dest_dir / name
    if not dest.exists():
        return dest
    stem, suffix = dest.stem, dest.suffix
    counter = 1
    while True:
        candidate = dest_dir / f"{stem} ({counter}){suffix}"
        if not candidate.exists():
            return candidate
        counter += 1

If Images/holiday.jpg already exists and a different holiday.jpg arrives, we must not destroy the first. So we try holiday (1).jpg, holiday (2).jpg, until we find a free name.

  • dest.stem is holiday, dest.suffix is .jpg, so the candidate is built by re-joining them with a number in between.
  • while True: with a return inside is the standard "search until found" pattern. The return is what ends the loop — it would spin forever without it.

Why not just let it overwrite? Because the app's job is to tidy your files. Silently deleting one would be unforgivable. This is the difference between a demo and something you would trust with real downloads.

5.6 Chunk 6 — reading the whole folder#

python
def read_folder(source: Path, cfg: dict):
    """Analyse every plausible downloaded file in `source`.

    Returns (files, skipped) where files is [(path, info), ...].
    """
    min_age = cfg.get("min_age_seconds", 5)
    files, skipped = [], []

    for entry in sorted(source.iterdir()):
        if not entry.is_file():
            continue
        ok, reason = looks_like_download(entry, min_age)
        if not ok:
            if reason != "system file":
                skipped.append((entry.name, reason))
            continue
        try:
            info = patterns.analyze(entry)
        except OSError:
            continue
        files.append((entry, info))

    return files, skipped

This is where the two earlier files meet. For each item in the folder:

  • sorted(source.iterdir()) — list the folder's contents in a stable order, so runs are repeatable and the output does not jump around.
  • if not entry.is_file(): continue — skip subfolders, only handle files.
  • Then the safety gate. Note we deliberately do not report system file as a skip — nobody wants a line about Thumbs.db every single run.
  • patterns.analyze(entry) — the detective from Part 3 does its work.
  • files.append((entry, info)) — keep the path and its signals together, in a tuple.

The result is everything the rest of the app needs, computed once.

5.7 Chunk 7 — picking the winning signal#

python
def _best_match(file_signals, mapping):
    """Pick the highest-priority signal present in `mapping`."""
    best, best_rank = None, -1
    for signal in file_signals:
        if signal in mapping:
            rank = patterns.SIGNAL_PRIORITY.get(signal.split(":", 1)[0], 0)
            if rank > best_rank:
                best, best_rank = signal, rank
    return best

A file can carry several signals; this finds the most trustworthy one that also appears in a given table (the user's rules, or the automatic table).

  • best, best_rank = None, -1 — a neat Python trick: assign two variables at once. We start the best rank at -1 so any real rank (0 or more) beats it.
  • signal.split(":", 1)[0] — grab the part before the colon (inner, name, …) to look up its priority. split(":", 1) splits on the first colon only.
  • .get(..., 0) — an unknown kind of signal ranks 0, harmlessly low.
  • if rank > best_rank — strictly greater, so the first signal wins any tie. Since we iterate a set, ties are rare and harmless.

This is the function that makes "we actually opened the file" beat "the name had a hint in it".

5.8 Chunk 8 — the version subfolder#

python
def _pick_version(file_signals):
    """The version number to use as a subfolder, if there is one."""
    versions = sorted(s.split(":", 1)[1] for s in file_signals
                      if s.startswith("version:"))
    return versions[-1] if versions else None

Collect every version: signal as a plain string (1.20, 1.20.1), sort them, and take the last one.

Why the last, not the first? Because Minecraft mod filenames look like jei-15.2.1-1.20.1.jar: the mod's own version comes first and the game version comes last. Sorted as text, 1.20 sorts before 1.20.1, and both sort after 15.2 would... but the point is that taking the last match of a 1.x pattern is far more reliable than the first. This one line is the difference between Minecraft Mods/1.20.1/ and Minecraft Mods/15.2/.

5.9 Chunk 9 — the decision itself#

def classify(path: Path, info: dict, cfg: dict, ext_lookup: dict) -> str:
    """Where should this file go? Returns a folder (maybe nested)."""
    sigs = patterns.signals(info)

    # 1. A rule you accepted for a suggestion.
    rule_map = {rule["match"]: rule["folder"] for rule in cfg.get("rules", [])
                if "match" in rule and "folder" in rule}
    matched = _best_match(sigs, rule_map)
    folder = rule_map.get(matched) if matched else None

    # 2. A pattern that sorts itself automatically.
    if not folder:
        matched = _best_match(sigs, patterns.AUTO_SIGNALS)
        folder = patterns.AUTO_SIGNALS.get(matched) if matched else None

This is the priority ladder from the top of the file, in code:

  1. Turn the user's rules into a lookup dictionary (signal -> folder).
  2. Ask _best_match which rule matches, if any.
  3. If a rule matched, use its folder.
  4. Otherwise try the automatic patterns.

The if matched else None guards against _best_match returning None (nothing matched) — you cannot look up None in a dictionary.

5.10 Chunk 10 — planning without moving#

def plan(source: Path, cfg: dict):
    """Work out every move without doing anything.

    Returns (moves, skipped, files):
      moves   - [(source_path, destination_path, folder), ...]
      skipped - [(name, reason), ...]
      files   - [(path, info), ...] used to build the pattern suggestions
    """
    ext_lookup = build_extension_lookup(cfg.get("categories", {}))
    target = resolve_target(cfg, source)

    files, skipped = read_folder(source, cfg)
    moves = []
    for path, info in files:
        folder = classify(path, info, cfg, ext_lookup)
        dest_dir = target / folder
        moves.append((path, unique_destination(dest_dir, path.name), folder))

    return moves, skipped, files

This separation is the best idea in the whole app. plan() decides everything but moves nothing. It returns the full list of intended moves.

That single design decision gives us, for free:

  • --dry-run (just print the plan instead of applying it),
  • the Scan button in the window,
  • a preview of any kind you ever want to add.

resolve_target is used before it is defined below — that is fine in Python, because functions are only looked up when they are called, not when the file is read.

def apply_moves(moves, cfg: dict, target=None):
    """Actually move the files and remember it so it can be undone."""
    done = []
    for src, dst, _folder in moves:
        try:
            dst.parent.mkdir(parents=True, exist_ok=True)
            shutil.move(str(src), str(dst))
            done.append((src, dst))
        except OSError as exc:
            print(f"  ! could not move {src.name}: {exc}")

    history.record(done)

    if cfg.get("cleanup_empty_folders", True) and target is not None:
        cleanup_empty_folders(target)
    return done
  • dst.parent.mkdir(parents=True, exist_ok=True) — make sure Images/ (and any parent like Minecraft Mods/1.20.1/) exists before moving into it.
  • shutil.move(str(src), str(dst)) — the actual move. It takes strings, hence str(...).
  • If one file fails, we print a warning and keep going. One locked file should not abandon the other ninety.
  • _folder — the folder name is part of each move tuple, but this function does not need it. The leading underscore says "intentionally unused".
  • history.record(done) — and now the move is undoable. Notice we record only the moves that actually succeeded.

def cleanup_empty_folders(root):
    """Remove category folders that ended up with nothing in them."""
    if root is None or not Path(root).is_dir():
        return
    for folder in sorted(Path(root).iterdir(), reverse=True):
        if folder.is_dir() and not any(folder.iterdir()):
            try:
                folder.rmdir()
            except OSError:
                pass

After a run, a category might be empty (say, the last image moved out). We remove it so your folder does not fill up with empty shells. reverse=True sorts backwards, which conveniently puts deeper names first. Same any(...iterdir()) check as before: only genuinely empty folders are removed, and only one level deep (unlike _prune_empty_parents, which climbs).

What is a class? A bundle of data and the functions that work on it. Here it is "the window and everything it can do". You build it once with App(root).

  • self — how a class refers to itself. self.root = root means "remember this window as my root". Every function in the class gets self first, and self.something is the object's own memory.
  • self.cfg = config.load() — settings loaded once, kept handy.
  • self.watching = False — are we in watch mode right now?
  • root.title(...), root.geometry("920x720"), root.minsize(...) — set the window title, its starting size, and the smallest it may be shrunk to.

    def find_patterns(self):
        self.save_settings(silent=True)
        source = organizer.resolve_source(self.cfg)

            messagebox.showerror("Folder not found", str(source))
            return
        self._set_status("looking for patterns...")

        def work():

            self.cfg["_ext_lookup"] = organizer.build_extension_lookup(
                self.cfg.get("categories", {}))

This is the most important concept in the whole window.

Scanning a big folder takes seconds. If we did it inside the click function, the window would freeze solid until it finished — Windows would even grey it out. So we run the work on a background thread:

  • def work(): — a function defined inside the method, holding the long job.
  • threading.Thread(target=work, daemon=True).start() — run work in parallel with the window. daemon=True means the thread is killed if you close the window, so it can never keep the app alive in the background.
  • self.root.after(0, lambda: self._show_patterns(found)) — the golden rule: you must never touch widgets from a background thread. root.after(0, ...) means "run this back on the main thread as soon as you can". That is the safe handover, and it is exactly why the window stays clickable while scanning.

If you remember one thing about GUI programming, make it this: background thread does the work, root.after hands the result back to the window. Do anything else and you get random freezes and crashes.

7.2 make_demo_files.py — a safe playground#

You cannot test a file organiser on your real Downloads folder while learning. This file builds a fake one, full of tricky files designed to exercise every part of the app.

python
"""Builds a fake Downloads folder so you can try the organizer safely.

Run me, then point the organizer at the folder it makes:

    python make_demo_files.py
    python organizer.py demo_downloads --dry-run
    python organizer.py demo_downloads --suggest

It creates small but REAL archives so the pattern detection has something
honest to chew on, plus a pile of ordinary files with realistic names.
"""

import os
import zipfile
from pathlib import Path

ROOT = Path(__file__).parent / "demo_downloads"
OLD = 1730000000  # old timestamp: stops the "still downloading" check skipping


def zip_file(name, contents):
    """Write a zip where contents is {inner path: bytes or str}."""
    path = ROOT / name
    with zipfile.ZipFile(path, "w") as zf:
        for inner, data in contents.items():
            if isinstance(data, str):
                data = data.encode("utf-8")
            zf.writestr(inner, data)
    os.utime(path, (OLD, OLD))


def raw(name, data):
    path = ROOT / name
    path.write_bytes(data)
    os.utime(path, (OLD, OLD))
  • zipfile.ZipFile(path, "w") — create a new zip ("w" = write). zf.writestr(inner, data) writes one file inside it.
  • isinstance(data, str) — if the content was given as text, encode it to bytes first, because zips store bytes.
  • os.utime(path, (OLD, OLD)) — set the file's access and modified times to an old timestamp. This is important: without it, the files would be brand new, and the engine's "skip files changed in the last 5 seconds" rule would skip

every one of them!

Now the files themselves. First the Minecraft-style packages, which should self-sort and gain version subfolders:

python

zip_file("sodium-fabric-1.20.1.jar", {
    "fabric.mod.json": '{"id":"sodium","depends":{"minecraft":">=1.20.1"}}',
    "sodium/Sodium.class": b"x",
})
zip_file("jei-1.20.1-forge.jar", {
    "META-INF/mods.toml": 'modLoader="javafml"',
    "mezz/jei/Jei.class": b"x",
})
zip_file("faithful-1.20.zip", {

Each one contains the one marker file that _inner_signals looks for. The names are realistic, including the version numbers, which is what lets us test both the pattern detection and the version-subfolder logic.

Then the patterns the app should suggest rather than assume:

python
# --- Patterns the user has NOT pre-approved: should become suggestions ----
# Factorio mods: recognised by info.json inside.
for i in range(3):
    zip_file(f"space-exploration-{i}.zip", {
        "info.json": '{"name":"space-exploration"}',
        "data.lua": "return {}",
    })
# RimWorld mods: recognised by About/About.xml.
for i in range(3):
    zip_file(f"rimhud-{i}.zip", {
        "About/About.xml": "<ModMetaData/>",
        "Assemblies/RimHUD.dll": b"MZ",
    })

Three of each, and that is not an accident. The engine only suggests a pattern when at least three files share a signal (min_pattern_files), so these loops create exactly enough to trigger it. Writing the files in a loop (for i in range(3)) keeps it short.

Finally, ordinary files that exercise the other rules:

Each raw(...) is a file containing the real signature bytes for its type, written with the b"..." shorthand plus b"\x00" * 40 to pad it out. They are not valid files in every case — a chair.glb is not a real 3D model — but they all start with the right bytes, which is exactly what we are testing.

Part 9 — Git and GitHub, properly explained#

Two different things, and confusing them is the usual reason beginners get stuck:

9.8 Passwords, tokens, and the thing that confuses everyone#

GitHub no longer accepts your account password for git push. You need a Personal Access Token:

  1. On GitHub: your picture → Settings → Developer settings → Personal access tokens → Tokens (classic) → Generate new token.
  2. Give it a name, tick the repo box, generate, and copy the token now — GitHub will not show it again.
  3. When Git asks for a password, paste the token instead.

Part 10 — When things go wrong#

python is not recognized The PATH checkbox was missed. Reinstall Python with "Add python.exe to PATH" ticked.

ModuleNotFoundError: No module named 'config' You are running the file from the wrong folder. cd into your project folder first — Python looks for import config in the folder you are standing in.

SyntaxError: invalid syntax pointing at a line you just typed Almost always a missing ), ] or }, or a missing quote. Count the brackets on the lines above. The error often shows up after the real mistake.

IndentationError: unexpected indent You mixed tabs and spaces, or used 2 spaces instead of 4. Select the whole file and re-indent consistently with 4 spaces.

PermissionError when moving a file The file is open in another program, or still downloading. Close it and retry. The app also skips recently-changed files for exactly this reason.

The window freezes when I click Scan You ran the work on the main thread instead of a background one. Check that the job is inside def work(): and started with threading.Thread(...).start(), and that widget updates go through self.root.after(0, ...).

A file went to the wrong folder That is feedback, not a bug. Add a rule in the Patterns tab, or add the missing extension to the right category. The app is designed to be taught.

The .exe says "Windows protected your PC" Normal for unsigned homemade programs. More info → Run anyway.

fatal: not a git repository You ran a Git command outside your project folder. cd into it first.

I messed up my files Click Undo last run, or run python organizer.py --undo. In future, always --dry-run first — that is what it is for.
